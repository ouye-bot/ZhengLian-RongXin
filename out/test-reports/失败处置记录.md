## 事件 1：performance 套件首跑 module1 全量失败（0/31110），module5/6/9 跳过

- **套件**：performance（test/performance-test.js）
- **用例**：module1 API并发热身与压测（低/中/高负载 + 30秒容量）、冷启动延迟、module5 用户信息查询并发、module6 安全中间件链路压测、module9 资源监控 —— 均依赖登录 Token
- **现象**：
  - 首跑（2026-11-02 09:42:21 本地，报告 benchmark-report-1793584313927.json）module1 起手即 `⚠ 用户创建/登录失败: Request failed with status code 500`（out/test-reports/performance.log 首跑被覆盖，失败快照见本记录与下方复现证据）；
  - 后续低/中/高负载与容量测试全部请求失败：容量段 `success=0, errors=31110, successRate=0.00`，`429: 0`（排除限流因素，为 401/500 类失败）；
  - module5/6/9 打印 `⚠️ 未获取到Token，跳过此模块`；
  - 报告 JSON 的 overallStatus 仍为 'success'（该套件未将 module1 成功率纳入总闸），属测试框架宽松判定，不据此掩盖失败。
- **根因**：环境/时序问题，非产品代码缺陷。机器在 02:36–09:41 间休眠，09:42:10 重启后端后仅 11 秒即被性能套件打满请求，此时 MySQL（portable 3307）尚处冷启动窗口，连接池首次建连超时（同机两次冷启动均出现 `创建数据库失败: Error: connect ETIMEDOUT`，backend/server.log 2026-11-01T18:31 与本次复现），登录链路返回 500，套件未取得 Token。
- **分类**：S3-d（环境/基建错）
- **改动文件**：无（不改代码，不记为契约失败）
- **处置**：重启后端并增加暖机步骤——等待 /health OK → 等待 server.log 出现「数据库表初始化成功」→ 实测 `POST /api/v1/auth/login`（perfuser）成功 → `GET /api/v1/pool`（带 Token）返回 200 → 确认新 server.log 零 ETIMEDOUT，再启动整套件。
- **复跑结果**：attempt 2（2026-11-02 10:01:24 本地启动）module1 `✓ 性能测试用户登录成功`，低/中/高负载 100/100、450/450、400/400 全部成功（429:0），容量 21050 请求 QPS=701.43、p99=16.12ms、100% 成功；module5/6/9 正常执行（详见 out/test-reports/performance.log 与 out/test-reports/performance-report.json）。
- **遗留观察（不构成本次失败）**：首跑期间曾出现一次非本执行员发起的后端进程更替（09:45:30 新 PID 14784 接管 3003 端口，父进程已消失，无法溯源；机器当日 09:38 有唤醒事件）。attempt 2 前已显式杀掉该进程并按 S1 流程重启（02:00:16，密钥校验通过、端口 3003、数据库表初始化成功），全程受控。
